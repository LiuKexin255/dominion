# Feature Specification: Guitar Deploy Failure Environment Diagnostics

**Feature Branch**: `032-guitar-deploy-failure-state`

**Created**: 2026-08-02

**Status**: Draft

**Input**: User description: "为 @tools/test/guitar/ 在执行部署**不成功**时打印环境状态，便于判断具体哪个 service 部署失败或者超时。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 打印部署失败时的环境状态 (Priority: P1)

作为测试工程师，当 `guitar run` 执行某个 suite 的部署步骤不成功时（环境部署失败、超时或其他部署错误），我需要在控制台输出中立即看到该环境的当前状态与失败详情，以便快速判断是哪个 service 部署失败或超时，而不必手动去翻查 deploy 工具的交错输出或另行查询。

**Why this priority**: 这是用户直接提出的痛点——部署失败时当前只返回一句错误信息（如超时），无法直观看出环境的最终状态、失败原因以及涉及哪些服务，直接影响大型测试失败时的排查效率。

**Independent Test**: 构造一个会在部署阶段失败的 suite（例如引用一个无法就绪的 service 或人为触发超时），运行 `guitar run <plan.yaml>`，观察控制台在部署失败后是否打印出清晰的环境状态诊断信息。

**Acceptance Scenarios**:

1. **Given** 一个 suite 的部署因环境达到失败终态而不成功, **When** 执行 `guitar run <plan.yaml>`, **Then** 在部署失败后控制台输出一段明确标记的环境状态诊断信息，其中包含目标环境名、环境的当前状态（如"失败"）以及失败原因说明，使用户能直接看出失败原因
2. **Given** 一个 suite 的部署因超时而不成功（环境仍处于"部署中"或"等待滚动发布"等非终态）, **When** 执行 `guitar run <plan.yaml>`, **Then** 输出的环境状态诊断信息显示环境当前处于非就绪的进行中状态，使用户能判断是部署未完成（超时）而非明确失败
3. **Given** 一个 suite 的部署不成功, **When** 输出的环境状态诊断信息, **Then** 信息中列出该环境本次部署所包含的服务（应用服务与基础设施），使用户能对照确认是哪个 service 出了问题
4. **Given** 一个 suite 的部署不成功, **When** 执行 `guitar run <plan.yaml>`, **Then** 在打印环境状态诊断信息后，仍继续执行该 suite 的清理步骤（删除环境），诊断信息不影响既有的清理流程
5. **Given** 一个 suite 的部署成功, **When** 执行 `guitar run <plan.yaml>`, **Then** 不打印失败环境状态诊断信息，输出行为与当前版本一致

---

### Edge Cases

- 当部署在环境创建之前就失败（例如镜像推送失败、deploy 配置解析错误、提交 desired state 时即报错）时，目标环境可能尚不存在或无可读取的状态——此时系统不得因查询状态而崩溃或掩盖原始错误，应以友好的方式说明无法获取环境状态。
- 当系统尝试获取环境状态本身失败（例如 deploy 服务暂时不可达）时，不得掩盖原始的部署失败错误；获取状态失败应被降级处理（如打印一条提示），原始错误仍作为 suite 失败原因上报。
- 当 suite 使用 `--suite` 过滤只执行单个 suite 且该 suite 部署失败时，环境状态诊断信息同样应被打印。
- 当输出被重定向到非终端（管道或文件）时，诊断信息应保持可读（遵循现有的颜色降级策略，不带 ANSI 颜色码）。
- 诊断信息的获取不得明显拖长整体失败响应时间（例如不应引入与部署超时同量级的额外等待）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 当 `guitar run` 中某个 suite 的部署步骤不成功（部署命令返回错误）时，系统必须在控制台输出一段明确标记的环境状态诊断信息，且该信息出现在原始部署错误被上报之前/与之清晰关联的位置。
- **FR-002**: 环境状态诊断信息必须至少包含：目标环境名（完整环境名）、环境的当前状态描述（如就绪/失败/部署中/等待滚动发布等）。
- **FR-003**: 当环境存在失败原因说明（failure message）时，诊断信息必须包含该原因说明，以帮助定位是哪个 service 或哪一步出了问题。
- **FR-004**: 诊断信息必须列出本次部署所涉及的服务集合（应用服务与基础设施服务），便于用户对照确认出问题的 service。
- **FR-005**: 当因环境尚未创建或状态不可读取而无法获取环境状态时，系统不得抛出异常或掩盖原始部署错误，应输出简短说明并继续以原始错误作为 suite 的失败原因。
- **FR-006**: 当获取环境状态的过程本身失败时，系统必须降级处理（输出提示而不中断），且不得改变 suite 最终上报的失败错误。
- **FR-007**: 打印环境状态诊断信息不得影响 suite 既有的清理流程——清理步骤仍正常执行。
- **FR-008**: 当部署成功时，系统不得输出失败环境状态诊断信息（保持与当前输出行为一致）。
- **FR-009**: 失败环境状态诊断信息必须遵循既有的颜色降级策略：在终端中可使用醒目颜色，在非终端/管道输出中自动禁用颜色码。

### Key Entities

- **环境状态 (Environment Status)**: 部署环境的运行时观测状态，包含整体状态（就绪、失败、部署中、等待滚动发布等）、失败原因说明、以及最近一次调和/成功时间。由部署服务在异步调和后产出。
- **部署服务集合 (Deployed Services)**: 一次部署所声明的服务集合，包含应用服务（artifact）与基础设施服务（infra），作为诊断时"涉及哪些 service"的依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 当 suite 部署因环境失败而不成功时，用户能从控制台输出的诊断信息中直接读出失败原因说明，无需另行手动查询 deploy 服务或翻查交错的部署日志。
- **SC-002**: 当 suite 部署因超时而不成功时，用户能从诊断信息中看出环境仍处于非就绪的进行中状态，从而区分"明确失败"与"超时未完成"。
- **SC-003**: 诊断信息中列出的服务集合与测试计划中该 suite 配置的部署服务一致，用户可据此定位具体出问题的 service。
- **SC-004**: 在所有部署不成功的场景下，suite 的清理流程仍照常执行，环境被正常回收（清理流程行为与未引入本特性时一致）。
- **SC-005**: 未使用本特性相关行为的既有测试计划（部署成功的正常路径）输出与当前版本完全一致，本特性对成功路径零影响。

## Assumptions

- 部署目标环境的完整环境名（含 scope 与本次 run 标识）在部署步骤启动前已由 `guitar` 生成并可知，因此部署失败后系统具备定位该具体环境的足够信息。
- 部署失败后的环境在清理（删除）之前仍可被查询其状态与失败原因；状态获取发生在清理之前。
- 环境状态诊断信息主要面向人工排查，输出位置为控制台标准输出（与现有 suite 输出一致），不引入新的持久化产物。
- 本特性仅作用于 suite 的"部署不成功"场景；测试阶段（test）失败不在本特性范围内（测试失败时环境通常已就绪，状态信息对排查帮助有限）。
- 诊断信息的获取时延应远小于部署本身的超时时长，不引入与部署超时同量级的额外等待。
