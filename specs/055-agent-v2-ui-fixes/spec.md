# Feature Specification: agent-v2 界面可用性修复（054 交付后 UI 缺陷）

**Feature Branch**: `055-agent-v2-ui-fixes`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "继续 @specs/054-agent-v2-bugfixes/ 完成后仍有一些优化 1. web 上错误和告警背景和字体相近，都是红色或都是黄色，字体颜色跟背景一样看不到字 2. agent 输出时，窗口滚动一致在底部，无法向上滚动，一滚动就被拉到底部。输出中持续在底部应当是在卡片中保持底部，而不是在整个窗口保持底部。3. desktop session 列表不会刷新，应当在进入 session 列表时刷新 4. web 在agent 思考过程输出时，会出现整个窗口的滚动条，这时滚动可以将整个页面向下滚动。只有思考过程输出时会有，message 输出时正常"

## Motivation

`specs/054-agent-v2-bugfixes/` 交付后，用户在实际环境使用中发现 4 个界面可用性缺陷（2026-09-05）：2 个 web 滚动行为缺陷使对话进行中的"回看阅读"不可用（输出期间无法向上滚动；思考流式期间整个窗口出现滚动条）、1 个状态呈现缺陷使失败/警示信息不可读（文字与背景同色）、1 个 desktop 列表数据新鲜度缺陷（返回列表不刷新）。本 feature 修复全部缺陷，使 054 交付的对话体验（分段呈现、失败内容保留、终止能力）真正可读、可回看、可信任。

缺陷定位（调研结论，作为修复背景）：

- **错误/警示横幅文字不可见**：web 以深色主题呈现（`projects/game/web/frontend/index.html` 静态 `data-ds-dark-theme`），该主题下设计 token 表（`projects/game/web/frontend/src/dsh-theme/design-platform.css`）定义 `--dsw-alias-state-error-primary` 与 `--dsw-alias-state-error-secondary` 解析为**同一颜色** red-400 `#f25a5a`；warn 的 primary（amber-500 `#f59e0b`）与 secondary（amber-400 `#f7ad31`）也近乎同色。而 `projects/game/web/frontend/src/theme.css` 中 `.chat-error`、`.presets-error`、`.agent-panel-error` 以 error-secondary 为背景 + error-primary 为文字，`.chat-canceled` 以 warn-secondary 为背景 + warn-primary 为文字——文字与背景同色/近色，用户完全看不到字。设计体系中深色主题下适合作状态填充底色的是深色调 token（如 warn-tertiary=amber-900、success-tertiary=green-900），当前选用的 token 组合在深色主题下不成立。
- **输出期间无法向上滚动**：`projects/game/web/frontend/src/components/ChatView.tsx` 的流式跟随滚动 effect 依赖 `[history, live, queue, error]`，每次内容变化（流式期间每个 chunk）都无条件执行 `scrollTop = scrollHeight` 贴底——用户向上滚动的任何尝试都被下一个 chunk 立即拉回底部。业界/上游 dsh 的既定模式是**条件跟随**：仅当滚动位置贴近底部时才跟随（上游实现见 [deepseek-harness ChatView.tsx](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/src/client/chat/ChatView.tsx) 的 `FOLLOW_THRESHOLD` + at-bottom 判定）。
- **desktop session 列表不刷新**：`projects/game/desktop/frontend/src/App.svelte` 的 `handleBackToSessions()` 返回列表时不触发 `handleRefresh()`——列表仅在应用挂载（onMount）与模板切换时加载；会话集合在会话期间发生变化（web 侧新建/删除、其他来源变更）后返回列表看到的仍是旧数据。
- **思考流式期间整个窗口出现滚动条**：仅在思考过程输出时出现，正文输出时正常（用户观察）。已知的改造偏差线索：web 的 ReasoningRow 样式改造自上游（attribution 见 `projects/game/web/frontend/README.md`），但丢失了上游折叠态的布局围栏——上游 [ReasoningRow.module.css](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/src/client/chat/ReasoningRow.module.css) 对折叠态根节点设 `contain: size layout` + 固定高度，使流式中的思考行不影响任何祖先布局；本地改造版（`projects/game/web/frontend/src/theme.css` 的 `.reasoning-row*` 规则）没有等价约束。用户补充（2026-09-05）：**折叠态与展开态均出现**全页面滚动条——根因不限于折叠态围栏缺失（展开态上游亦无围栏）；两态共有而正文输出所无的因素（如 running 扫描动画 `::after` 挂于两态均存在的行容器上、其颜色写法与上游不同）为高优先候选。精确断点以 plan 阶段实际环境复现排查为准（覆盖两态），spec 只约束可观测结果（窗口不可滚动）。

**追加范围（2026-09-05 plan 阶段用户指令）**：除缺陷修复外，系统性审计 web 前端与 dsh-web 上游（deepseek-harness）在**交互逻辑**上的偏差——凡改造传承自上游的交互组件（对话滚动、思考折叠行等），除已记录的有意偏离外，交互逻辑一律与上游保持一致，审计识别的偏差一并修复；未移植的上游产品能力（富输入、附件、丰富工具视图等）不纳入对齐范围。审计结论与偏离清单固化于 feature 文档（research.md / contracts/）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 输出期间滚动行为正确：跟随不劫持、滚动约束在消息区内 (Priority: P1) 🎯 MVP

agent 输出期间（思考流式、正文流式、工具过程、排队指示任一阶段），对话**消息区**是唯一垂直滚动面：浏览器窗口（页面整体）MUST NOT 出现滚动条、MUST NOT 可整体滚动（含思考过程输出时——修复当前"思考输出出现整个窗口滚动条"的缺陷）。消息区的**贴底跟随以用户位于底部为条件**：用户在（或贴近）底部时，新内容自动跟随保持底部；用户向上滚动后，自动跟随 MUST 停止——阅读位置不被后续输出拉回；用户滚回底部后，跟随恢复。跟随停止期间（非贴底时），消息区呈现**"回到底部"浮动按钮**，点击即回底并恢复跟随（对齐上游交互，2026-09-05 澄清）。用户自己发送新消息时，视角回到底部（自己的消息可见）。

**Why this priority**: 用户报告的核心体验缺陷：输出进行中"一滚动就被拉到底部"使回看阅读完全不可用——对话产品的阅读流是最基本的使用路径；且思考流式期间窗口级滚动条破坏页面布局。两者共同定义"输出期间滚动"这一个交互模型，合并为一个故事交付。

**Independent Test**: 组件级验证（驱动流式回合输出）：断言 (a) 位于底部时新内容保持贴底；(b) 上滚后阅读位置保持、不被拉回；(c) 回底后跟随恢复；(d) 非贴底时"回到底部"按钮呈现、贴底时不呈现、点击回底并恢复跟随；(e) 发送新消息后回到底部。思考流式与正文流式两种输出阶段分别断言。布局约束（页面整体无垂直溢出）以部署环境人工验证记录闭合（组件级测试无布局引擎，2026-09-05 澄清）。

**Acceptance Scenarios**:

1. **Given** 一轮 agent 回合正在流式输出（正文），**When** 用户位于消息区底部，**Then** 新内容增长时视图保持贴底（跟随生效）。
2. **Given** 一轮回合流式输出中，**When** 用户向上滚动到历史内容，**Then** 阅读位置保持，后续新输出不将视图拉回底部（跟随停止）。
3. **Given** 用户已上滚（跟随停止），**When** 用户滚回（或贴近）底部，**Then** 自动跟随恢复，后续新内容重新贴底。
4. **Given** 用户已上滚（跟随停止），**When** 用户发送新消息，**Then** 视角回到底部，自己的新消息可见。
5. **Given** 用户已上滚（非贴底），**When** 查看消息区，**Then** "回到底部"浮动按钮呈现；点击后视角回到底部、跟随恢复；回到贴底状态后按钮不再呈现。
6. **Given** 思考过程正在流式输出（折叠态），**When** 输出持续增长，**Then** 浏览器窗口不出现滚动条、页面整体不可滚动，所有滚动只发生在消息区内。
7. **Given** 思考过程流式输出中，**When** 用户展开思考体查看完整内容，**Then** 窗口同样不出现滚动条（展开体的增长被消息区滚动面容纳）。
8. **Given** 回合结束后（含错误横幅、终止标识、排队指示呈现时），**When** 用户查看页面，**Then** 窗口无滚动条、页面整体不可滚动。

### User Story 2 - 错误与警示状态文字可读 (Priority: P1)

web 上所有以状态色填充呈现的提示（错误横幅——回合失败/列表加载失败/物化失败/终止请求失败；警示呈现——"已终止"标识、排队提示等），其**文字与背景对比充分**：在任何输出场景下用户都能读到提示文字，不再出现"文字颜色跟背景一样看不到字"。错误与警示两类状态在修复后仍保持色系可区分（红/黄语义不变），只是各自内部的底色-文字组合达到可读对比。

**Why this priority**: 用户报告的直接可见缺陷：回合失败时错误横幅上的错误信息完全不可读——错误信息是失败排查的第一入口（054 刚交付了"失败内容保留"，如果保留下来的失败提示读不了，那套能力打折扣）。修复面小、独立可交付。

**Independent Test**: 对全部状态横幅样式计算文字色与背景色的对比度，断言达到可读标准（WCAG AA 正文口径 ≥ 4.5:1）；人工验证错误横幅、"已终止"标识、排队提示文字清晰可读。

**Acceptance Scenarios**:

1. **Given** 一轮回合以失败结束，**When** 错误横幅呈现在对话页，**Then** 错误文案文字与背景对比充分、清晰可读。
2. **Given** 一轮回合被用户终止，**When** "已终止"标识呈现，**Then** 其文字清晰可读，且视觉上与错误横幅可区分（警示色系 vs 错误色系）。
3. **Given** preset 管理页或 agent 设置面板中发生加载/提交失败，**When** 错误提示呈现，**Then** 文字清晰可读。
4. **Given** 排队提示等以警示色呈现的状态，**When** 呈现于消息区，**Then** 文字清晰可读。
5. **Given** 状态横幅长时间/多行内容（如带堆栈的错误详情），**When** 呈现，**Then** 每一行文字都保持可读（不因换行/滚动部分失效）。

### User Story 3 - desktop session 列表进入即刷新 (Priority: P2)

desktop 上用户从 session 详情返回 sessions 列表时，列表**自动刷新**为最新会话集合——web 侧（或其它来源）新建、删除的会话在返回列表时立即反映，无需重启应用或切换模板。既有刷新时机（应用启动加载、模板切换重列）保持不变；刷新失败呈现既有错误语义且不清空已呈现的列表。

**Why this priority**: 桌面端是扫雷链路的执行终端，session 列表是连接入口；数据陈旧会让用户选错/找不到目标会话。但 desktop 的使用流（进入列表→选会话→连接）受影响频率低于 web 侧两个 P1 缺陷，且修复独立、面小。

**Independent Test**: 建立已知会话集合 → 进入某 session → 在外部（如 web 侧）新建/删除会话 → 返回列表 → 断言列表反映最新集合；断言应用启动与模板切换的既有刷新行为不回归。

**Acceptance Scenarios**:

1. **Given** 用户位于某 session 详情页，会话集合在外部发生变化（新建/删除），**When** 用户返回 sessions 列表，**Then** 列表自动刷新，呈现最新会话集合。
2. **Given** 会话集合无变化，**When** 用户返回列表，**Then** 列表内容与刷新前一致（刷新无副作用、不丢失滚动/状态异常）。
3. **Given** 返回列表时刷新请求失败，**When** 失败发生，**Then** 按既有错误语义呈现（错误提示 + 日志），已呈现的旧列表不被清空。
4. **Given** 刷新进行中用户立即点击某会话进入，**When** 刷新响应随后落地，**Then** 用户的选择与进入流程不受干扰（不被顶回列表、不中断连接）。
5. **Given** 应用启动加载与模板切换两个既有刷新时机，**When** 触发，**Then** 刷新行为与呈现与现状一致（零回归）。

### User Story 4 - 传承组件交互逻辑与 dsh-web 对齐 (Priority: P2)

对 web 前端中**改造传承自 dsh-web 上游**的交互组件做系统性对齐审计并修复偏差：审计识别的交互逻辑偏差（如思考折叠行缺失布局围栏、跟随摘要机制偏离、扫描动画颜色硬编码、折叠开关视觉形态等）修复至与上游一致；确属有意的偏离（如思考体 markdown 渲染、工具卡简化形态、输入区单行简化、文案本地化口径等）以**偏离清单**形式文档固化——此后"传承组件与上游不一致"只有两种合法状态：已对齐，或在清单中登记了偏离理由。

**Why this priority**: 2026-09-05 plan 阶段用户追加指令：修复不一致（除可记录的有意偏离外，交互逻辑与 dsh-web 保持一致）。对齐消除"同一交互两套行为"的认知与维护成本，且本次四项缺陷中两项（滚动跟随、思考行布局）本身就是偏离上游所致——审计是防止同类缺陷再发的系统性手段。修复项多数与 US1/US2 同文件耦合交付，独立价值在于审计完整性与清单固化。

**Independent Test**: 审计清单驱动的对照验证：修复项以组件级测试断言对齐后的行为（围栏样式存在、跟随条件、回底入口等）；偏离清单与实际代码逐项对照成立（清单外无未声明偏差）。

**Acceptance Scenarios**:

1. **Given** 审计识别的传承组件交互偏差清单（固化于 feature 文档），**When** 本 feature 交付，**Then** 清单中标记为"修复"的偏差全部修复，交互行为与上游一致（组件级测试断言）。
2. **Given** 审计识别的有意偏离项（如思考体 markdown、工具卡简化、单行输入），**When** 偏离清单呈现，**Then** 每项含偏离理由与上游对照来源，且代码实际行为与清单声明一致。
3. **Given** 后续对传承组件的改动，**When** 引入与上游的新交互偏差，**Then** 偏差要么对齐上游、要么先登记清单（流程约束，验收为清单成为后续维护的对照基线）。
4. **Given** 未移植的上游产品能力（富输入 composer、附件、丰富工具视图等），**When** 审计呈现，**Then** 明确标注为"未移植/不在对齐范围"，不产生部分移植的中间态。

### Edge Cases

- **跟随判定边界**："贴近底部"的判定阈值（多大范围内视为贴底、恢复跟随）由实现定义；可观测约束为——用户明显离开底部（超过一屏的少部分）即停止跟随，回到底部附近即恢复，阈值不应大到"感觉已经离开底部却仍被拉回"、也不应小到"回底了还不跟随"。
- **回合结束时的视角**：用户已上滚（跟随停止）时回合结束（错误/终止横幅出现），视角保持原位不跳变（用户在回看历史，不被终态横幅的出现强行拉底）；横幅本身在消息区内可滚动到达。
- **回底入口的存在条件**：仅以滚动位置（非贴底）为判定，与回合状态（运行中/已结束）无关——回合结束后非贴底时"回到底部"按钮同样呈现且可用。
- **空会话与短内容**：内容不足以滚动时无滚动条、无跟随副作用；跟随逻辑不产生异常滚动位置。
- **横向溢出**：超长不可断行内容（如长坐标串、URL、无空格长 token）不撑破横向布局——文档横向同样不产生滚动条，消息区/卡片内自行容纳（横向滚动或截断由既有样式语义决定）。
- **多会话切换**：切换会话/重进会话时视角回到底部（回填最新内容可见），既有回填行为零回归。
- **状态横幅的呈现主题**：web 当前为深色单一主题；对比度修复以当前呈现主题为准验收，不引入浅色主题切换面（是否预留 token 语义正确性由 plan 决策）。
- **desktop 刷新与模板切换并发**：返回列表与切换模板同时发生时刷新不重复叠加产生错误状态（以最后一次操作的目标模板列表为准）。
- **desktop 列表加载态**：返回触发的刷新呈现既有加载语义（如加载指示），不阻塞页面返回（先返回、列表异步刷新）。

## Requirements *(mandatory)*

### Functional Requirements

#### 滚动行为（用户问题 2 + 4）

- **FR-001**: agent 输出全程（思考流式含展开体、正文流式、工具卡片、排队指示、错误/终止横幅），对话消息区 MUST 是唯一垂直滚动面：浏览器窗口 MUST NOT 出现垂直滚动条、页面整体 MUST NOT 可滚动。实现方 MUST 排查并修复思考流式期间布局逃逸到文档层的缺陷（以实际环境复现确认根因，不得凭推测改代码）。
- **FR-002**: 消息区滚动跟随 MUST 以用户位于底部为条件：位于（或贴近）底部时新内容自动贴底；用户向上滚动离开底部后 MUST 停止自动贴底（阅读位置不被后续输出改变）；用户回到（或贴近）底部后 MUST 恢复跟随。
- **FR-003**: 用户发送新消息时 MUST 将消息区视角带回底部（新消息可见）；既有排队输入、终止等交互行为零回归（054 FR-015/016/017 语义不变）。
- **FR-004**: 跟随停止期间（消息区非贴底时）MUST 呈现"回到底部"浮动入口：点击后视角回到底部并恢复跟随；贴底期间该入口 MUST NOT 呈现（2026-09-05 澄清，对齐上游 `!atBottom` 回底交互）。

#### 状态提示可读性（用户问题 1）

- **FR-005**: 全部以状态色填充呈现的横幅/提示（对话错误横幅、"已终止"标识、preset 管理错误、agent 设置面板错误、排队提示等）MUST 满足文字-背景可读对比：对比度 ≥ 4.5:1（按 web 实际呈现主题计算）；MUST NOT 出现文字与背景同色/近色不可读的组合。
- **FR-006**: 修复 MUST 保持状态语义的视觉区分：错误（红色系）与警示（黄色系）修复后仍为可区分的不同色系；成功/中性等其余既有状态色使用不回归。

#### desktop 列表刷新（用户问题 3）

- **FR-007**: desktop 从 session 详情返回 sessions 列表时 MUST 自动刷新列表（反映最新会话集合）；既有启动加载与模板切换刷新语义零回归；刷新失败按既有错误语义呈现且不清空已呈现列表；刷新进行中用户选择会话进入不受干扰。

#### 交互对齐（plan 阶段追加，用户问题 5）

- **FR-009**: 改造传承自 dsh-web 上游的交互组件（对话滚动、思考折叠行及审计识别的其余传承项）MUST 与上游交互逻辑对齐：审计识别的偏差 MUST 修复（组件级测试断言对齐后的行为）；确属有意的偏离 MUST 登记偏离清单（含偏离理由与上游对照来源），MUST NOT 存在清单之外的未声明交互偏差；未移植的上游产品能力 MUST 标注为不在对齐范围，不引入部分移植的中间态。

#### 范围与验收

- **FR-008**: 修复 MUST 附带相应测试：滚动跟随行为（条件跟随、回底恢复、回底入口呈现/点击、新消息回底——组件级断言）、状态横幅对比度（可计算的对比度口径断言——组件级）、desktop 进入列表刷新（含失败与既有时机回归）；布局约束（页面整体无垂直滚动）以部署环境人工验证记录闭合（2026-09-05 澄清——组件级测试无布局引擎，不引入浏览器 E2E 基建）；054 交付的对话行为（分段/折叠/markdown/终止/内容保留）与既有组件、store 测试零回归。

### Key Entities

- **状态横幅（State Banner）**: 错误/警示/终止终态的用户可见呈现单元——文案 + 底色/文字的配色语义对；本 feature 约束其可读性（对比度）与类别区分度。
- **跟随滚动（Follow Scroll）**: 消息区滚动位置与内容增长的联动行为，由"是否贴底"条件门控——停止/恢复跟随的判定与非贴底期间的"回到底部"入口是本 feature 的行为实体。
- **滚动范围（Scroll Containment）**: 页面滚动面的归属约束——垂直滚动唯一归属于对话消息区，文档/窗口不参与滚动。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 输出期间滚动行为修复：思考流式（含展开）与正文流式全程页面整体无垂直滚动（部署环境人工验证记录，2026-09-05 澄清）；位于底部时保持贴底、上滚后位置保持不被拉回、回底后跟随恢复、非贴底时"回到底部"入口可用、发新消息回底（组件级行为断言）。
- **SC-002**: 状态提示可读性清零"看不到字"：全部状态横幅文字-背景对比度 ≥ 4.5:1（组件级断言 + 人工验证记录），错误与警示色系仍可区分。
- **SC-003**: desktop 列表新鲜度：外部变更会话集合后返回列表立即反映最新状态（人工验证记录），既有刷新时机零回归。
- **SC-004**: 既有行为零回归：049/051/054 既有组件与 store 测试全部通过；对话语义（分段/折叠/markdown/终止/内容保留/排队）、preset 管理、session 删除编排与 054 交付一致。
- **SC-005**: 传承组件交互对齐闭环：审计清单中标记"修复"的偏差全部落地并有组件级测试断言；偏离清单文档化且与代码实际行为逐项一致；清单外无未声明的交互偏差（审计复查记录）。

## Assumptions

- **A1（跟随滚动交互模型，对齐上游）**: 条件跟随的交互模型对齐 dsh 上游 ChatView 的既定实现（at-bottom 判定 + 阈值内跟随 + 非贴底期间的"回到底部"浮动入口，[deepseek-harness ChatView.tsx](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/src/client/chat/ChatView.tsx)）；"用户发送新消息回到底部"为该模型的组成部分（自己的新消息应可见）。阈值取值与回底入口的位置/样式由 plan 阶段决策（Edge Cases 已约束可观测边界）。
- **A2（对比度标准）**: 可读性以 WCAG AA 正文口径（4.5:1）为可测下限；具体配色来源（深色调底 + 亮色字，沿用设计 token 体系）由 plan 阶段决策——本 feature 只约束可读结果与色系区分，不约束具体 token 选择。
- **A3（思考输出窗口滚动条根因开放）**: 用户观察补充（2026-09-05）：**折叠态与展开态均出现**全页面滚动条、正文输出正常——根因不限于折叠态围栏缺失（F1），两态共有的 running 扫描动画（`::after`，两态行容器均存在、正文输出无此元素）为高优先候选；已知改造偏差线索（本地 ReasoningRow 折叠态缺失上游 `contain: size layout` 布局围栏，见 [上游 ReasoningRow.module.css](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/src/client/chat/ReasoningRow.module.css)）。精确断点以 plan/实现阶段实际环境复现排查为准（隔离实验见 research.md §2.3），spec 只约束可观测结果（FR-001），不预设根因（同 054 A3 的开放式定位风格）。
- **A4（desktop 刷新时机范围，2026-09-05 用户裁定）**: 刷新时机为"进入 sessions 列表"（返回导航），不扩展到窗口聚焦，不引入周期性轮询/推送刷新；列表仍为只读控制面（`specs/051-agent-v2-dsh-migration/contracts/desktop-bridge.md` §5 语义不变）。
- **A5（大型测试与布局验收，2026-09-05 用户裁定）**: 本 feature 为 web/desktop 前端 UI 缺陷修复，不改变服务行为；验收以组件级测试 + 人工验证记录为主——布局约束（页面整体无垂直滚动）以部署环境人工验证记录闭合，不引入浏览器 E2E 基建——054 既有 testplan suites 作为回归面零回归（如涉及部署调整则同步更新）。
- **A6（交互对齐审计范围，2026-09-05 plan 阶段用户指令）**: 审计范围限定为"改造传承自 dsh-web 上游"的交互组件（判定依据 `projects/game/web/frontend/README.md` Attribution 及组件源码注释中的上游来源链接）；上游未移植的产品能力（contentEditable 富输入 composer、附件/文件消息、MessageIconActions、ToolRow 丰富工具视图、模型重试倒计时等）属产品能力差异，不纳入对齐；具体修复项与偏离清单见 `specs/055-agent-v2-ui-fixes/research.md` 与 `specs/055-agent-v2-ui-fixes/contracts/ui-interactions.md`。
