# Data Model: gRPC-JS Build Support

**Branch**: `003-grpc-js-support` | **Date**: 2026-06-03

## Build Pipeline Entities

### 1. Proto Definition (`.proto` file)

Source of truth for service contracts and message types.

| Field | Type | Description |
|-------|------|-------------|
| path | file path | Location in source tree (e.g., `experimental/ts/grpc_hello_world/greeter.proto`) |
| package | string | Protobuf package name (e.g., `experimental.ts.grpc_hello_world`) |
| services | list\<Service\> | gRPC service definitions |
| messages | list\<Message\> | Protobuf message definitions |
| imports | list\<string\> | Imported proto files (e.g., `google/api/annotations.proto`) |

### 2. Proto Library Target (`proto_library`)

Bazel target that defines the proto compilation unit.

| Field | Type | Description |
|-------|------|-------------|
| name | string | Target name (e.g., `greeter_proto`) |
| srcs | list\<file\> | `.proto` source files |
| deps | list\<target\> | Dependent proto_library targets (e.g., googleapis) |

### 3. TypeScript Proto Types (generated `.ts` files)

Generated by `proto-loader-gen-types` from proto definitions. These files provide compile-time TypeScript typing for dynamically loaded proto services; they are not static protobuf or gRPC stub implementations.

| File Pattern | Description |
|-------------|-------------|
| `ProtoGrpcType.ts` | Master type — the type of the loaded package definition |
| `{Package}/{Message}.ts` | Input message interface (proto3 fields optional) |
| `{Package}/{Message}__Output.ts` | Output message interface (all fields present) |
| `{Package}/{Service}.ts` | Service client + handler interfaces |
| `{Package}/{Enum}.ts` | Enum type definition |

**Validation rules**:
- Generated files MUST NOT be committed to source control
- Generated files reside exclusively in `bazel-out/`
- Regenerated on proto changes via Bazel's incremental build

### 4. Compiled JavaScript (`ts_project` output)

TypeScript source compiled to CommonJS JavaScript.

| Field | Type | Description |
|-------|------|-------------|
| `.js` files | output | CommonJS modules (ES2020 target) |
| `.d.ts` files | output | TypeScript declaration files |
| source_map | boolean | Source maps for debugging |

Compiled JavaScript emitted from generated type files is a normal TypeScript compilation artifact and is not part of the proto/gRPC code generation contract.

### 5. gRPC Service Server

Runnable Node.js process implementing gRPC service handlers.

| Field | Type | Description |
|-------|------|-------------|
| entry_point | string | Main module path (e.g., `src/server.js`) |
| proto_path | string | Path to proto file in runfiles |
| handlers | object | Implementation of service RPC methods |
| port | number | Server listen port |

### 6. Testplan Acceptance

Repository testplan assets that launch the TypeScript gRPC service plus an HTTP wrapper as the system under test. Deploy exposes the testplan-owned wrapper over HTTP; the wrapper verifies the grpc-js service by forwarding HTTP requests to gRPC internally.

| Field | Type | Description |
|-------|------|-------------|
| deploy_plan | file path | Deployment material used by the testplan to launch the service |
| http_endpoint | string | Public HTTP wrapper endpoint provided to the test case by the testplan environment |
| wrapper_service | file path | Go HTTP wrapper that bridges HTTP requests to grpc-js `SayHello` |
| test_case | file path | Go HTTP large-test case that sends the acceptance request to the wrapper |
| expected_response | string | Expected HTTP response message (`Hello World`) |

## File Flow Relationships

```
greeter.proto
    │
    ├─[proto_library]──────────────────────────────────┐
    │                                                  │
    └─[ts_proto_library]──→ generated .ts types        │
                                │                      │
    src/server.ts ──────────────┤                      │
                                │                      │
                          [ts_project + swc]            │
                                │                      │
                          .js + .d.ts files             │
                                │                      │
                          [js_binary]                   │
                                │                      │
                          runnable server ──→ loads greeter.proto at runtime
                                                    via @grpc/proto-loader
                                 │
                                 ├── [Go HTTP wrapper] HTTP /say-hello → gRPC SayHello
                                 │
                                 └── [testplan] launches service + suite wrapper and verifies HTTP response
```

## Key Entity: ts_proto_library Rule

The custom Bazel rule that bridges proto_library and TypeScript compilation.

| Attribute | Type | Required | Description |
|-----------|------|----------|-------------|
| name | string | yes | Target name |
| proto | label | yes | proto_library target to generate types from |
| grpc_lib | string | no | gRPC library import path (default: `@grpc/grpc-js`) |
| longs | string | no | int64 output representation (default `String`) |
| enums | string | no | enum output representation (default `String`) |
| defaults | bool | no | output default values (default `True`) |
| oneofs | bool | no | output virtual oneof fields (default `True`) |
| keep_case | bool | no | preserve proto field names; must match runtime `keepCase` (default `False`) |

| Output | Description |
|--------|-------------|
| `.ts` files | Generated TypeScript type definitions for dynamic proto loading |

## State Transitions

### Proto → Generated Types → Compiled Service

```
[IDLE] .proto file exists
  │
  ├── bazel build :greeter_types ──→ [GENERATED] .ts type files exist in bazel-out
  │
  ├── bazel build :server ─────────→ [COMPILED] .js + .d.ts in bazel-out
  │
  ├── bazel run :run ──────────────→ [RUNNING] gRPC server listening on port
  │
  └── guitar/testplan run ─────────→ [ACCEPTANCE] service + suite HTTP wrapper launched as SUT
                                        │
                                        └── client calls wrapper HTTP endpoint ──→ wrapper calls gRPC ──→ [RESPONDED] server replies
```
