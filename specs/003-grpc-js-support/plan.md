# Implementation Plan: gRPC-JS Build Support & Example Service

**Branch**: `003-grpc-js-support` | **Date**: 2026-06-03 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/003-grpc-js-support/spec.md`

**Note**: This plan follows the user's guidance to reference official grpc-node documentation (https://github.com/grpc/grpc-node) and use Bazel for all compilation, with custom rules as needed.

## Summary

Add protobuf-to-TypeScript type generation support to the Bazel build system using the officially recommended `@grpc/grpc-js` + `@grpc/proto-loader` dynamic-loading stack. Create a custom `ts_proto_library` Bazel rule that wraps `proto-loader-gen-types` to generate TypeScript type files from `.proto` files for compile-time checking only. Implement an example gRPC service in TypeScript under `experimental/ts/grpc_hello_world/` that demonstrates the full pipeline: proto definition → type generation → TypeScript compilation → runtime `.proto` loading → runnable gRPC server verified through a repository testplan. Static JavaScript or TypeScript protobuf/gRPC stub generation is out of scope.

## Implementation Phases

### Phase A: Custom Bazel Rule — `ts_proto_library`

**Goal**: Create a reusable Bazel rule that generates TypeScript type definitions from `.proto` files.

**Files to create/modify**:
- `tools/proto/ts_proto_library.bzl` — Rule implementation
- `tools/proto/BUILD.bazel` — Build file

**Rule behavior**:
1. Accepts `proto_library` target as input (reads `ProtoInfo` provider)
2. Extracts direct proto sources and transitive dependencies (for include path resolution)
3. Runs `proto-loader-gen-types` (from `@grpc/proto-loader` npm package) via Bazel executable action with `--outDir` set to the declared Bazel output directory
4. Declares `.ts` output files under a `generated/` layout matching the protobuf package hierarchy
5. Provides generated `.ts` type files as outputs consumable by `ts_project`; it does not generate static JavaScript or TypeScript protobuf/gRPC stubs

**Key implementation detail**: `proto-loader-gen-types` resolves proto imports relative to the working directory. The rule must stage proto files (including transitive deps like googleapis) in a directory structure that matches the import paths. This is achieved by creating a TreeArtifact with the correct layout before invoking the tool. The generation flags and runtime `protoLoader.loadSync` options must remain identical: `longs=String`, `enums=String`, `defaults=true`, `oneofs=true`, and `keep_case=false`/omitted runtime `keepCase`; `grpcLib=@grpc/grpc-js` is passed for generation. If `keep_case` is ever enabled, runtime `keepCase: true` must also be enabled.

**Verification**: `bazel build //experimental/ts/grpc_hello_world:greeter_types` produces `.ts` files.

### Phase C: TypeScript Server Implementation

**Goal**: Implement the gRPC server in TypeScript using generated types.

**Files to create**:
- `experimental/ts/grpc_hello_world/src/server.ts` — Server implementation

**Server implementation pattern** (official grpc-node recommendation):
1. Load proto dynamically with `@grpc/proto-loader` from a deterministic runfiles path
2. Cast loaded package to generated `ProtoGrpcType`
3. Implement service handlers using generated handler interfaces
4. Register handlers and start server

**Runtime proto requirement**: `greeter.proto` must be included in the binary's runfiles/data. If a runtime-loaded proto imports Google API annotations or other transitive protos, those import files must also be available to `protoLoader.loadSync` through `includeDirs`. The example proto is intentionally simple; FR-003 is verified by a dedicated build-only annotation fixture.

**Update BUILD.bazel**: Add `ts_project` target (with SWC transpiler) and `js_binary` target. Generated type imports from `src/server.ts` use `../generated/...`, so `tsconfig.json` must include both `src/**/*.ts` and `generated/**/*.ts` and must not constrain `rootDir` to `src`.

**Verification**: `bazel build //experimental/ts/grpc_hello_world:server` succeeds.

### Phase D: Testplan Acceptance

**Goal**: Write a testplan that verifies the grpc-js server through a deployed HTTP wrapper, because deploy exposes HTTP routes but not raw gRPC endpoints. The wrapper must run as a separate service owned by the testplan suite and forward HTTP requests to the internal TypeScript gRPC service.

**Files to create**:
- `experimental/ts/grpc_hello_world/service/service.yaml` — Deployment material for the TypeScript grpc-js server
- `experimental/ts/grpc_hello_world/testplan/wrapper/main.go` — test-suite Go HTTP wrapper that translates HTTP requests to `SayHello` gRPC calls
- `experimental/ts/grpc_hello_world/testplan/wrapper/BUILD.bazel` — test-suite Go wrapper binary/image targets and generated Go proto/grpc client deps
- `experimental/ts/grpc_hello_world/testplan/wrapper/service.yaml` — test-suite HTTP wrapper deployment material with an exposed `http` port
- `experimental/ts/grpc_hello_world/testplan/deploy.yaml` — Demo deployment material that deploys both grpc-js service and HTTP wrapper; only the wrapper has the public HTTP route
- `experimental/ts/grpc_hello_world/testplan/BUILD.bazel` — Go `go_largetest` case target
- `experimental/ts/grpc_hello_world/testplan/interface_test.yaml` — Testplan definition exposing the wrapper HTTP endpoint
- `experimental/ts/grpc_hello_world/testplan/interface_test.go` — Go HTTP acceptance case using `common/gopkg/testtool`

**Test approach**:
1. Build the TypeScript server artifact through Bazel
2. Build the Go HTTP wrapper artifact through Bazel
3. Launch the grpc-js service and suite wrapper through the repository testplan/deploy workflow
4. Configure the wrapper to reach the grpc-js service through the in-cluster service DNS/port for `service/service.yaml`
5. Resolve the public HTTP wrapper endpoint from the testplan-provided environment with `common/gopkg/testtool`
6. Send an HTTP request such as `GET /say-hello?name=World` to the wrapper using a 5-second client deadline
7. Wrapper sends `SayHello` to the grpc-js service over gRPC and returns `Hello World` as HTTP response
8. Let the testplan workflow clean up the service and suite wrapper

**Update BUILD.bazel**: Add the targets needed for the server artifact, testplan wrapper image, Go proto/grpc wrapper client generation, and `go_largetest` case. Do not add a unit test that starts the service process in-process.

**Verification**: The TypeScript demo testplan runs successfully through guitar/testplan and `bazel test //experimental/ts/grpc_hello_world/testplan:testplan_test --config=largetest` passes.
