# Spike Findings: protoc-gen-go-aip Bazel codegen

**Date**: 2026-08-01
**Plugin**: `github.com/protoc-contrib/protoc-gen-go-aip` v0.1.3
**Goal**: Validate that `protoc-contrib/protoc-gen-go-aip` integrates with this repo's
Bazel (`rules_go`) proto pipeline and generates the type-safe resource-name API
(`ParseSessionName(s) (SessionName, error)`) intended to replace the hand-written
`projects/game/pkg/gameconst/const.go`.

All findings below are **empirically confirmed** by this spike
(`experimental/golang/aip_codegen/`), which builds and tests green under Bazel.

---

## TL;DR

The integration is **viable**. protoc-contrib/protoc-gen-go-aip works through
`rules_go`'s `go_proto_compiler` rule, wired via **gazelle directives** (the same
mechanism already used for grpc / grpc-gateway). The generated API is exactly the
desired shape, is self-contained (stdlib only), and for our proto shapes the
plugin emits **only** the resource file — so the single-suffix Bazel concern is
moot.

---

## F1. Plugin dependency wiring (go.mod `tool` directive)

The plugin is a `main` package that no Go source in the repo imports, so a plain
`go get` leaves it pruneable and its transitive deps (e.g.
`github.com/iancoleman/strcase`, `go.einride.tech/aip`) do not enter the module
graph → building the plugin via go_deps fails with "unknown repo
`com_github_iancoleman_strcase`".

**Fix (confirmed):** pin the plugin with Go 1.24+'s `tool` directive, pointing at
the **main package path** (not the module root):

```
bazel run //:go -- get -tool github.com/protoc-contrib/protoc-gen-go-aip/cmd/protoc-gen-go-aip@v0.1.3
```

This adds a `tool (...)` block to go.mod, preserves the full closure in go.sum,
and `bazel mod tidy` surfaces the binary target
`@com_github_protoc_contrib_protoc_gen_go_aip//cmd/protoc-gen-go-aip:protoc-gen-go-aip`
(builds green via go_deps).

## F2. Bazel compiler rule (go_proto_compiler)

A `go_proto_compiler` wraps the plugin binary — exactly the grpc-gateway
precedent (`@grpc_ecosystem_grpc_gateway//protoc-gen-grpc-gateway:go_gen_grpc_gateway`):

```bzl
load("@rules_go//proto:compiler.bzl", "go_proto_compiler")

go_proto_compiler(
    name = "go_gen_aip",
    plugin = "@com_github_protoc_contrib_protoc_gen_go_aip//cmd/protoc-gen-go-aip:protoc-gen-go-aip",
    suffix = "_aip.pb.resource.go",
)
```

Notes:
- `suffix = "_aip.pb.resource.go"` is the file extension rules_go declares as the
  expected output (base filename `game` → `game_aip.pb.resource.go`). Source:
  `@rules_go//proto:compiler.bzl` v0.60.0 — `go_proto_compile` iterates
  `suffix`/`suffixes` and declares one expected file each.
- **No `deps` needed** on the compiler: the generated resource code is
  self-contained (imports only stdlib `fmt` and `strings`).

## F3. ⚠ KEY: compilers must be wired through gazelle directives, not hand-written

`rules_go` `go_proto_library` `compilers` is **regenerated by gazelle**. A
hand-written `compilers = [..., ":go_gen_aip"]` is **stripped** on the next
`bazel run //:gazelle` unless the compiler is declared in a gazelle directive.
This was the single hardest-won lesson of the spike: after a gazelle run the aip
compiler silently disappeared, only `.pb.go` compiled, and the generated aip
symbols became "undefined".

The repo uses this pattern in the root `BUILD.bazel`. Two directives matter:
- `go_grpc_compilers` → applied to go_proto_library **with services** (game.proto,
  deploy.proto, mongo_demo, ...).
- `go_proto_compilers` → applied to go_proto_library **without services**
  (this demo).

**Production wiring (DONE):** the `go_gen_aip` compiler target lives in the root
`BUILD.bazel`, and is appended to **both** root directives so it applies
workspace-wide regardless of whether a proto defines services:

```
# gazelle:go_proto_compilers @rules_go//proto:go_proto, //:go_gen_aip
# gazelle:go_grpc_compilers @rules_go//proto:go_grpc_v2, @rules_go//proto:go_proto, @grpc_ecosystem_grpc_gateway//protoc-gen-grpc-gateway:go_gen_grpc_gateway, //:go_gen_aip
```

Running `bazel run //:gazelle` then adds `//:go_gen_aip` to every
`go_proto_library` `compilers` list automatically.

## F4. Multi-file output concern: RESOLVED (single suffix suffices)

protoc-gen-go-aip can emit up to three companion files:
`*_aip.pb.resource.go`, `*_aip.pb.query.go`, `*_aip.pb.fieldmask.go`. The query
and fieldmask files are **conditional**: query only when a `filter`/`order_by`
field carries the `(protoc_contrib.aip.field_reference)` option; fieldmask only
for qualifying AIP-134 update requests.

**Spike result:** with our proto shapes (resources + `resource_reference` +
`UpdateTeamProfileRequest`-style update + `FieldMask`), the plugin emitted
**only** `*_aip.pb.resource.go`. No query, no fieldmask. The single-suffix
`go_proto_compiler` builds cleanly. The multi-file Bazel risk is therefore moot
for the game.proto resource set.

**Resource-less protos are safe (confirmed workspace-wide):** for a proto with no
`google.api.resource` messages the plugin emits a 2-line
`// +build ignore` / `package ignore` stub — so rules_go's expected output exists
but Go excludes it from compilation. Applying the compiler to every proto
workspace-wide (via the root directives) breaks nothing.

**AIP-123 gotcha surfaced:** `projects/infra/deploy/deploy.proto` had non-conformant
resource `type` strings — `infra.liukexin.com/deploy/Environment` — where the kind
(`deploy/Environment`) contains a `/`. The plugin splits the type on the first `/`
and derives the function name from the kind, producing invalid Go
(`Parsedeploy/EnvironmentName`). Fixed by moving `deploy` into the service name
(DNS-style): `deploy.infra.liukexin.com/Environment` /
`deploy.infra.liukexin.com/ServiceEndpoints` (7 occurrences in deploy.proto).
Per [AIP-123](https://google.aip.dev/123) the type must be
`{service_name}/{Type}` with a single PascalCase `Type` (no `/`).

## F5. Generated API shape (confirmed by compiling + testing)

For a single-pattern multi-segment resource `templates/{template}/sessions/{session}`:

```go
type SessionName struct {
    TemplateID string   // pattern var {template} → field TemplateID
    SessionID  string   // pattern var {session}  → field SessionID
}

func ParseSessionName(s string) (SessionName, error)
func ParseFullSessionName(s string) (SessionName, error)   // "//svc/..." form

func (n SessionName) String() string          // round-trips back to the name
func (n SessionName) FullName() string
func (n SessionName) Validate() error         // empty / '/' checks per segment
func (n SessionName) Type() string            // "spike.liukexin.com/Session"
func (n SessionName) Pattern() string
func (n SessionName) ContainsWildcard() bool  // AIP-159 "-"
func (n SessionName) MarshalText() / UnmarshalText

func (x *Session) ParseName() (SessionName, error)         // on the proto msg
func (x *Session) ParseFullName() (SessionName, error)
```

- **Trailing-literal singleton works**: `Team` pattern
  `templates/{template}/sessions/{session}/team` generates `TeamName{TemplateID,
  SessionID}`; `ParseTeamName` validates the literal `team` segment and
  `String()` reconstructs it. This directly covers game.proto's `Team` resource.
- **`resource_reference` → `ParseName()` delegation**: a field annotated with
  `google.api.resource_reference` gains a `ParseName()` (or `Parse<Field>()`)
  method on the owning message that delegates to the referent's parser.
- **`Parent()`**: generated only when the resource's parent pattern matches
  another declared resource in the same compilation unit.
- Field-naming: pattern variables get an `ID` suffix (`{template}` →
  `TemplateID`), per the AIP convention.

## F6. Migration impact on gameconst (preview)

The hand-written `projects/game/pkg/gameconst/const.go` parsers map cleanly:

| gameconst (hand-written) | generated (aip) |
|---|---|
| `SessionName(template, sessionID) string` | `SessionName{TemplateID, SessionID}.String()` |
| `SessionID(name) (template, sessionID, err)` | `ParseSessionName(name) → {TemplateID, SessionID}` |
| `TeamSessionID(name) (...)` | `ParseTeamName(name)` (trailing `team` literal handled) |
| `MessageAgentParse(name)` | `ParseMessageName(name)` |
| `TeamProfileID(name)` | `ParseTeamProfileName(name)` |

Call sites: `session/handler`, `proxy/handler`, `prompt/handler` (~11 sites) +
`gameconst` self-tests. `gameconst` keeps its non-resource constants (gRPC
targets, log fields, path-segment literals). Pure Go-side change; the TS agent
is unaffected (it does not parse Go resource names).

## F7. Demo artifacts

- `aip_codegen.proto` — two demo resources mirroring game.proto shapes:
  `Session` (`templates/{template}/sessions/{session}`, two variables) and
  `Team` (`.../team`, trailing-literal singleton).
- `BUILD.bazel` — minimal: the aip compiler is applied automatically by the
  repo-wide `go_proto_compilers` directive (no local compiler/directive). The
  `annotations_go_proto` dep is pinned with `# keep` (the generated `.pb.go`
  imports the genproto annotations package even though the `.proto` does not
  import `annotations.proto` directly).
- `aip_codegen_test.go` — exercises `ParseSessionName` / `ParseTeamName`,
  round-trip `String()`, `Validate()`, the trailing-literal singleton, and error
  cases. **Passes.**

The `go_proto_compiler` target itself (`//:go_gen_aip`) lives in the root
`BUILD.bazel` (repo config), not in this demo package.
